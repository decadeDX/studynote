# 数据交换格式

数据交换格式是一套约定，用来把程序中的对象、配置或消息转换成可存储、可传输的文本，使不同语言、不同系统都能理解同一份数据。

例如：Java 后端不能直接把一个 `User` 对象通过网络交给 JavaScript 前端。后端通常先把对象转换为 JSON 字符串，前端收到后再将 JSON 字符串还原为 JavaScript 对象。

```text
Java 对象
   ↓ 序列化
JSON/XML 文本
   ↓ 通过 HTTP、消息队列或文件传输
JSON/XML 文本
   ↓ 反序列化
JavaScript、Python、Java 等语言中的对象
```

- **序列化**：把程序中的对象转换为 JSON、XML 等文本。
- **反序列化**：读取 JSON、XML 文本，并将其转换为程序中的对象。

常见的数据交换格式有：

1. **JSON**：结构简洁、体积较小，是现代 Web 开发中最常用的格式。
2. **XML**：使用标签描述数据，结构严谨，常用于配置文件、文档交换和传统企业系统。

## JSON

JSON（JavaScript Object Notation，JavaScript 对象表示法）是一种轻量级的文本数据交换格式。

虽然 JSON 的语法来源于 JavaScript，但它并不属于某一种编程语言。Java、Python、JavaScript、C# 等语言都可以解析和生成 JSON。

### 一个完整示例

```json
{
  "id": 1001,
  "name": "张三",
  "enabled": true,
  "roles": ["admin", "editor"],
  "address": {
    "province": "浙江省",
    "city": "杭州市"
  },
  "profile": null
}
```

最外层的 `{}` 表示一个对象，对象内部包含多组“键和值”。

|     | 键         | 值                     | 值的类型 | 含义      |
| :-- | :-------- | :-------------------- | :--- | :------ |
|     | `id`      | `1001`                | 数字   | 用户编号    |
|     | `name`    | `"张三"`                | 字符串  | 用户姓名    |
|     | `enabled` | `true`                | 布尔值  | 账号是否启用  |
|     | `roles`   | `["admin", "editor"]` | 数组   | 用户拥有的角色 |
|     | `address` | `{...}`               | 对象   | 用户地址    |
|     | `profile` | `null`                | 空值   | 暂无个人资料  |

### JSON 的两种基本结构

JSON 主要使用两种结构组织数据：**对象**和**数组**。二者可以相互嵌套。

#### 1. 对象

对象使用一对花括号 `{}` 表示，内部由若干组“键值对”组成。

```json
{
  "key1": "value1",
  "key2": "value2",
  "key3": "value3"
}
```

基本规则：

- 键和值之间使用冒号 `:` 分隔。
- 多组键值对之间使用逗号 `,` 分隔。
- **键必须是字符串，并且必须使用英文双引号 `"` 包围。**
- 最后一组键值对后面不能添加逗号。
- 同一个对象中的键应当保持唯一，否则不同解析器可能产生不同结果。

正确示例：

```json
{
  "name": "李四",
  "age": 20
}
```

错误示例：

```text
{
  name: "李四",       // 错误：键没有使用双引号
  'age': 20,          // 错误：标准 JSON 不能使用单引号
  "enabled": true,   // 错误：最后一项后面多了逗号
}
```

> [!warning] 注意
> 上面的错误示例使用 `text` 代码块，是因为它不是合法 JSON。JSON 本身也不支持 `//` 或 `/* ... */` 注释。

#### 2. 数组

数组使用一对方括号 `[]` 表示，内部可以存放零个或多个值。

```json
["Java", "MySQL", "Spring Boot"]
```

多个值之间使用逗号 `,` 分隔。数组中的值可以是任意合法的 JSON 类型，也可以混合使用不同类型。

```json
[
  "张三",
  20,
  true,
  null,
  { "city": "杭州" },
  [80, 90, 100]
]
```

实际开发中，为了使结构更统一、后续处理更方便，通常让同一个数组中的元素具有相同含义和相似结构。

对象数组示例：

```json
[
  {
    "id": 1,
    "name": "张三"
  },
  {
    "id": 2,
    "name": "李四"
  }
]
```

这个数组包含两个用户对象，常见于接口返回的列表数据。

### JSON 支持的数据类型

JSON 的值只能是以下六种类型：

|     | 类型  | 示例                       | 说明                                |
| :-- | :-- | :----------------------- | :-------------------------------- |
|     | 字符串 | `"hello"`                | 必须使用英文双引号，不能使用单引号                 |
|     | 数字  | `18`、`3.14`、`-5`、`1.2e3` | 不区分整数和小数类型，不能写 `NaN` 或 `Infinity` |
|     | 布尔值 | `true`、`false`           | 必须使用小写，不能写成 `True` 或 `False`      |
|     | 空值  | `null`                   | 表示没有值，必须使用小写                      |
|     | 对象  | `{ "name": "张三" }`       | 由键值对组成                            |
|     | 数组  | `[1, 2, 3]`              | 由多个值组成                            |

JSON 不直接支持日期、二进制、函数和注释，需要由通信双方约定表示方式。例如日期通常表示为字符串：

```json
{
  "createdAt": "2026-10-08T10:30:00+08:00"
}
```

接收方读取后，再将字符串转换为对应语言中的日期对象。

### 字符串与转义字符

字符串内部如果需要出现双引号、换行或反斜杠，就要使用反斜杠 `\` 转义。

|     | 写法       | 表示的内容            |
| :-- | :------- | :--------------- |
|     | `\"`     | 双引号              |
|     | `\\`     | 反斜杠              |
|     | `\n`     | 换行               |
|     | `\t`     | 制表符              |
|     | `\u4e2d` | Unicode 字符，例如“中” |

```json
{
  "message": "他说：\"你好！\"",
  "path": "C:\\Users\\demo",
  "content": "第一行\n第二行"
}
```

### 嵌套结构

对象的值可以是另一个对象或数组，数组的元素也可以是对象或数组，因此 JSON 能表示较复杂的数据。

```json
{
  "className": "软件工程 1 班",
  "students": [
    {
      "id": 1,
      "name": "张三",
      "scores": [88, 92, 95]
    },
    {
      "id": 2,
      "name": "李四",
      "scores": [85, 90, 91]
    }
  ]
}
```

读取数据时可以按照层级逐步定位：

```text
className                     → 软件工程 1 班
students[0].name              → 张三
students[1].scores[2]         → 91
```

其中数组下标通常从 `0` 开始。

### JSON 的常见使用场景

- 浏览器前端与后端接口之间传递数据。
- REST API 的请求体和响应体。
- 微服务之间传递消息。
- 保存应用程序配置。
- 将结构化数据暂存到文件或数据库。

### JSON 的优点与局限

**优点：**

- 语法简洁，标签少，便于阅读和传输。
- 与多数编程语言中的对象、数组结构容易对应。
- 解析工具多，是 Web API 的主流格式。

**局限：**

- 标准 JSON 不支持注释，不适合需要大量说明的手写配置。
- 不支持日期、二进制等专用类型，需要额外约定。
- 本身只描述数据，不负责定义字段是否必填、长度范围等规则；严格校验通常需要 JSON Schema。

## XML

XML（Extensible Markup Language，可扩展标记语言）使用标签、属性和嵌套结构描述数据。

```xml
<?xml version="1.0" encoding="UTF-8"?>
<user id="1001">
  <name>张三</name>
  <enabled>true</enabled>
  <roles>
    <role>admin</role>
    <role>editor</role>
  </roles>
</user>
```

### XML 的基本组成

#### 1. XML 声明

```xml
<?xml version="1.0" encoding="UTF-8"?>
```

- `version="1.0"` 表示使用 XML 1.0 规范。
- `encoding="UTF-8"` 表示文件采用 UTF-8 字符编码。
- XML 声明通常写在文件第一行，但并非所有场景都强制要求。

#### 2. 元素

元素由开始标签、内容和结束标签组成：

```xml
<name>张三</name>
```

- `<name>` 是开始标签。
- `张三` 是元素内容。
- `</name>` 是结束标签。

没有内容的元素可以写成自闭合形式：

```xml
<remark />
```

#### 3. 属性

属性写在开始标签内部，用来补充元素的信息：

```xml
<user id="1001" enabled="true">
  <name>张三</name>
</user>
```

其中 `id` 和 `enabled` 是 `user` 元素的属性。属性值必须使用引号包围。

#### 4. 根元素

一个格式正确的 XML 文档只能有一个根元素，所有其他元素都必须包含在根元素中。

正确示例：

```xml
<users>
  <user>张三</user>
  <user>李四</user>
</users>
```

错误示例：

```text
<user>张三</user>
<user>李四</user>
```

错误示例中存在两个并列的顶级元素，没有唯一根元素。

### XML 的基本语法规则

- 标签必须正确闭合。
- 标签名称区分大小写，`<User>` 和 `<user>` 是两个不同标签。
- 元素必须正确嵌套，不能交叉闭合。
- 属性值必须使用单引号或双引号包围。
- XML 文档必须有且只有一个根元素。

正确嵌套：

```xml
<user>
  <name>张三</name>
</user>
```

错误嵌套：

```text
<user>
  <name>张三</user>
</name>
```

### XML 特殊字符转义

部分字符在 XML 中有特殊含义，作为普通文本使用时需要转义。

|     | 原字符 | 转义写法     | 含义  |
| :-: | :-: | :------- | :-- |
|     | `<` | `&lt;`   | 小于号 |
|     | `>` | `&gt;`   | 大于号 |
|     | `&` | `&amp;`  | 与号  |
|     | `"` | `&quot;` | 双引号 |
|     | `'` | `&apos;` | 单引号 |

```xml
<condition>age &gt; 18 &amp;&amp; age &lt; 60</condition>
```

解析后的文本内容是：

```text
age > 18 && age < 60
```

### XML 注释

XML 支持注释：

```xml
<!-- 用户基本信息 -->
<user>
  <name>张三</name>
</user>
```

注释不能嵌套，注释内容中也不能出现连续的 `--`。

### XML 的常见使用场景

- Maven 的 `pom.xml`、Spring 早期配置等配置文件。
- SOAP Web Service。
- 企业系统和旧系统之间的数据交换。
- SVG、Office Open XML 等文档格式。
- 需要命名空间、XSD 校验或文档型结构的数据。

### XML 的优点与局限

**优点：**

- 标签语义明确，适合表示层级复杂的文档。
- 支持注释、属性、命名空间。
- 可以通过 XSD 或 DTD 描述和校验文档结构。
- 在企业集成、行业标准和旧系统中拥有成熟生态。

**局限：**

- 开始标签和结束标签较多，数据通常比 JSON 更冗长。
- 默认情况下元素内容都是文本，具体数据类型需要额外定义。
- 解析和配置通常比 JSON 复杂。

## 用 JSON 和 XML 表示同一份数据

以下两段内容都表示一个编号为 `1001`、姓名为“张三”、拥有两个角色的用户。

### JSON 写法

```json
{
  "id": 1001,
  "name": "张三",
  "roles": ["admin", "editor"]
}
```

### XML 写法

```xml
<user>
  <id>1001</id>
  <name>张三</name>
  <roles>
    <role>admin</role>
    <role>editor</role>
  </roles>
</user>
```

JSON 使用对象、键值对和数组组织数据；XML 使用元素、标签和层级关系组织数据。

## JSON 与 XML 对比

|     | 对比项  | JSON                      | XML                    |
| :-- | :--- | :------------------------ | :--------------------- |
|     | 基本结构 | 对象和数组                     | 元素、属性和嵌套标签             |
|     | 语法   | 简洁、轻量                     | 标签化、较详细                |
|     | 数据类型 | 内置字符串、数字、布尔值、`null`、对象和数组 | 元素内容默认是文本，可通过 XSD 定义类型 |
|     | 注释   | 标准 JSON 不支持               | 支持 `<!-- ... -->`      |
|     | 结构校验 | 可使用 JSON Schema           | 可使用 XSD、DTD            |
|     | 命名空间 | 不内置                       | 原生支持                   |
|     | 文件体积 | 通常较小                      | 标签较多，通常较大              |
|     | 可读性  | 适合数据对象和接口响应               | 适合文档和具有明确标签语义的内容       |
|     | 常用场景 | REST API、前后端通信、配置、消息      | SOAP、文档交换、企业集成、传统配置    |

## 选型建议

- Web 接口、微服务通信和普通配置：通常优先选择 JSON。
- 已有协议明确要求 XML：继续使用 XML，不必为了追求简洁强行替换。
- 需要 XSD、命名空间、SOAP 或复杂文档标准：选择 XML。
- 需要传输图片、音频等二进制内容：通常使用专门的二进制协议，或者约定 Base64、文件地址等表示方式。
- 不要只根据文件大小选择格式，还应考虑既有协议、校验要求、工具生态和上下游兼容性。

## 与 HTTP 的关系

JSON 和 XML 是数据的**表示格式**，HTTP 是数据的**传输协议**，二者不是同一层面的概念。

HTTP 请求或响应通常使用 `Content-Type` 告诉接收方正文采用什么格式：

```http
Content-Type: application/json; charset=UTF-8
```

```http
Content-Type: application/xml; charset=UTF-8
```

例如，一个 JSON 接口响应可能是：

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=UTF-8

{
  "code": 200,
  "message": "success",
  "data": {
    "id": 1001,
    "name": "张三"
  }
}
```

## 与 MySQL 的关系

- MySQL 提供原生 `JSON` 类型，可以检查写入内容是否为合法 JSON，并使用 JSON 函数查询其中的数据。
- JSON 字段适合保存结构可能变化、又不经常参与复杂关联查询的附加信息。
- 经常用于查询、排序、分组或建立约束的关键数据，通常更适合拆成普通列，而不是全部塞入一个 JSON 字段。
- MySQL 没有与 JSON 类型完全对应的原生 XML 字段类型；完整 XML 通常保存为 `TEXT`。
- 如果需要频繁查询 XML 中的某些属性，应考虑将这些属性拆分为独立列或关联表。

## 安全注意

- 不要信任外部传入的 JSON 或 XML，应校验字段、类型、长度、取值范围和必填项。
- 对输入设置最大长度和最大嵌套深度，避免超大数据或深层嵌套消耗过多内存。
- 反序列化时只允许需要的类型，避免不安全的任意类型反序列化。
- 解析不可信 XML 时应禁用外部实体，防止 XXE（XML External Entity）攻击。
- 不要将未经处理的 JSON/XML 内容直接拼接到 SQL、HTML 或系统命令中。
- 日志中不要直接记录密码、令牌、身份证号等敏感字段。

## 常见错误速查

|     | 错误                | 原因                | 正确做法                    |
| :-- | :---------------- | :---------------- | :---------------------- |
|     | JSON 键写成 `name`   | 键没有使用双引号          | 写成 `"name"`             |
|     | JSON 字符串使用 `'张三'` | 标准 JSON 不支持单引号字符串 | 写成 `"张三"`               |
|     | JSON 最后一项后有逗号     | 标准 JSON 不允许尾随逗号   | 删除最后一个逗号                |
|     | JSON 中写了注释        | 标准 JSON 不支持注释     | 将说明写到文档中或改用支持注释的配置格式    |
|     | XML 标签没有闭合        | XML 要求标签成对或自闭合    | 使用 `</tag>` 或 `<tag />` |
|     | XML 标签交叉嵌套        | 元素没有按层级关闭         | 先关闭内层元素，再关闭外层元素         |
|     | XML 中直接写 `<`、`&`  | 与 XML 语法冲突        | 使用 `&lt;`、`&amp;` 转义    |
